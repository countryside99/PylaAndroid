# AGENTS.md — Creating PylaAndroid Playstyles

Guide for AI agents (Claude, ChatGPT, Codex, or any other) that help people create, change and
check PylaAndroid `.pyla` playstyles using the **Playstyle Studio** builder.

> **The one-sentence version:** a playstyle is generated by the builder's `generate()` function from
> 12 settings; you choose settings, you do not invent code. Check the result with the tools
> listed here, and say honestly what was and was not proven.

## 1. Project Overview

**PylaAndroid** is an Android bot app that plays automatically. Its behavior can be customized with
**playstyles**: small `.pyla` script files that the user imports in the app
(*Playstyles → Import custom .pyla*). ✅ Confirmed (source: README, index.html guide)

**Playstyle Studio** (`index.html`) is a single offline HTML page that turns a handful of settings
into a `.pyla` file. It needs no server, account, library or network (it ships a Content-Security-Policy with
`connect-src 'none'`). ✅ Confirmed (source)

The Android app itself, its script interpreter (`PyLexer` / `PyParser`), its importer
(`PlaystyleImporter`) and its brawler catalog **were not supplied**. They are named in the README
only. ❓ Unknown — see §4 and §14.

## 2. Purpose of This Document

This file lets an agent with no prior knowledge:

1. understand what a `.pyla` file is and what the builder can produce;
2. turn a person's plain-language wishes ("play safe", "chase enemies") into builder settings;
3. generate, modify and validate playstyles without inventing features;
4. report honestly how much of "it works" is proven.

**Priorities, in order:** (1) real compatibility with PylaAndroid, (2) honesty about evidence,
(3) simplicity, (4) creativity. Never trade a higher priority for a lower one.

## 4. Playstyle Architecture

### 4.1 Four layers of "correct"

Do not mix these up. Passing a lower layer never implies a higher one.

| # | Layer | What it means | Who can prove it |
|---|---|---|---|
| 1 | **Valid file structure** | One-line JSON header, then a script body, LF, UTF-8 | `verify.js`, the lint snippet in Appendix B |
| 2 | **Valid configuration values** | All 12 settings inside the allowed ranges and types | `validateConfig()` (throws on bad input) |
| 3 | **Valid behavioral logic** | Settings do not contradict each other; the behavior matches what the user asked for | Your own reasoning using §7 and §10 |
| 4 | **Actual PylaAndroid compatibility** | The app imports it, parses it, and runs it as intended | **Only** the Android Gradle test or the real app. Not provable from the supplied files |

### 4.2 Pipeline

```
12 settings ──validateConfig()──▶ cleaned settings ──generate()──▶ one text file
                 (throws on error)                              line 1: JSON header
                                                                line 2+: script body
```

- ✅ Confirmed (source): `generate()` always calls `validateConfig()` first.
- ✅ Confirmed (source): the file is plain text. The browser download uses MIME
  `application/octet-stream` and the file name from `fileName()`.
- ✅ Confirmed (source): everything in the body is a fixed template. Only a few numbers and
  optional blocks change with the settings.

### 4.3 What the exported script does each cycle

Priority order (✅ Confirmed (source), read from the generated body):

1. **Poison gas** (only if "React to detected poison gas" is on): if any gas is detected,
   move using the gas vector. This **overrides everything else**, including attacking-distance logic.
2. **Enemy visible**: keep the preferred distance (approach / retreat / strafe-or-hold).
3. **No enemy**: do the idle behavior (`explore`, `stay`, or `follow`).
4. **Safety filter**: the wanted direction is tried at 8 rotations (0°, ±45°, ±90°, ±135°, 180°).
   The first one that is not toward detected gas and not blocked by a known wall is used. If none is
   safe the result is `(0, 0)` (stand still).
5. **Attack (independent of movement)**: if the closest enemy is within attack range and
   hittable, request a normal auto-aim attack. Hold/release is handled for brawlers the catalog
   marks as "must hold".
6. **Optional abilities** (gadget / hypercharge / super), only if enabled.

Consequence: *every* preset attacks whenever an enemy is in range. Presets only change **where the
brawler moves**, not whether it fires. ✅ Confirmed (source, arithmetic)

## 5. Complete Playstyle Schema

### 5.1 Header (line 1)

One line of JSON, produced by `JSON.stringify` of exactly these keys in exactly this order:

| Key | Type | Value produced by the builder | Notes |
|---|---|---|---|
| `name` | string | The user's name, trimmed, 1–80 chars | Required, non-empty |
| `description` | string | Auto-generated: `Android v4.0.0 builder 1.0; distance {range}% of attack range; {idle} when no target; strafe {on/off}.` | Do not hand-write it |
| `brawlers` | array of strings | Always `["all"]` | See §8 |
| `gamemodes` | array of strings | Always `["all"]` | See §8 |
| `author` | string | The author, or `"Custom"` if blank | ≤ 80 chars |

✅ Confirmed (source + run). No other header keys exist in the generator. Adding any is
❌ Unsupported.

### 5.2 Body (line 2 onward)

- Starts with four `#` comment lines ("Generated for PylaAndroid v4.0.0 …").
- Defines helpers (`reference_move`, `gas_clear`, `checked_move`), reads the game state, decides
  movement, then decides attacks.
- Uses 4-space indentation, no tabs.
- The file ends with exactly one `\n`. ✅ Confirmed (run: last bytes of `example-export.pyla`).
- No BOM, no `\r`, no NUL. ✅ Confirmed (source: verify.js, run).

### 5.3 What is NOT in the schema

There is no JSON body, no list of rules, no `if/then` config format, no per-brawler tables, no
priorities list. The "playstyle data structure" is *the 12 settings below plus a fixed template*.

## 6. Supported Properties and Values

These 12 settings are the **complete** input surface. ✅ Confirmed (source: `fields` array in the UI
and `validateConfig`).

| Setting | Type | Allowed | UI step | Default (Balanced) | Effect |
|---|---|---|---|---|---|
| `name` | string | 1–80 chars, no control chars (U+0000–U+001F, U+007F) | — | `My Android Playstyle` | Header name; also the download file name |
| `author` | string | 0–80 chars, no control chars | — | empty → `Custom` | Header author |
| `range` | number | 20 – 110 | 1 | 85 | Preferred distance, **% of the brawler's attack range** |
| `band` | number | 0 – 30 | 1 | 12 | Tolerance, **% of attack range**, on both sides of `range` |
| `strafe` | boolean | `true` / `false` (real booleans only) | — | true | Sideways movement inside the band |
| `period` | number | 0.5 – 6 | 0.5 | 2 | Seconds between strafe direction flips. Ignored if `strafe` is false |
| `idle` | string | exactly `stay`, `follow`, `explore` | — | `explore` | What to do when no enemy is detected |
| `leash` | number | 1 – 8 | 0.5 | 3 | Follow distance in **tiles**. Used only when `idle` is `follow` |
| `gas` | boolean | `true` / `false` | — | true | React to detected poison gas |
| `super` | boolean | `true` / `false` | — | false | Auto-Super |
| `gadget` | boolean | `true` / `false` | — | false | Auto-Gadget |
| `hyper` | boolean | `true` / `false` | — | false | Auto-Hypercharge |

Behavior of the validator (✅ Confirmed (run)):

- Out-of-range numbers, `NaN`, `Infinity`, empty strings, unknown `idle`, non-boolean toggles, empty
  or multi-line names are **rejected with an error**.
- Numbers are rounded to 2 decimals (e.g. `range: 85.555` → `85.56`; in the script it becomes `0.8556`).
- Numeric **strings** such as `"85"` are accepted for numeric fields, but strings such as `"true"`
  are **not** accepted for booleans. Always send real numbers and real booleans.
- Unknown extra properties (e.g. `"evil": "x"`) are **silently ignored**. They do not become part
  of the output, so never rely on them and never add them.
- `period` and `leash` are still validated even when unused, so keep them in range.

### 6.1 Presets

✅ Confirmed (source). A preset only fills settings; it is not stored in the file.

| Preset | range | band | strafe | period | idle | leash | gas | super / gadget / hyper |
|---|---|---|---|---|---|---|---|---|
| `balanced` | 85 | 12 | on | 2 | explore | 3 | on | off |
| `kiter` | 95 | 8 | on | 2 | stay | 3 | on | off |
| `rusher` | 45 | 15 | off | 2 | explore | 3 | on | off |
| `team` (Team follower) | 85 | 12 | on | 2 | follow | 3 | on | off |
| `guard` | 95 | 10 | off | 2 | stay | 3 | on | off |

Choosing a preset in the UI does not change `name` or `author`.

## 7. Behavioral Configuration

### 7.1 Distance logic (when an enemy is detected)

Let `desired = attack_range × range/100` and `margin = attack_range × band/100`.
✅ Confirmed (source):

| Situation | Movement |
|---|---|
| `distance > desired + margin` | Move **toward** the enemy |
| `distance < desired − margin` (floored at 0) | Move **away** from the enemy |
| Otherwise, `strafe` on | Move perpendicular to the enemy; direction flips every `period` s |
| Otherwise, `strafe` off | No movement (stand still) |

The "enemy" is only ever **the closest enemy** found by the engine's `find_closest_enemy`.
There is no target selection or priority setting. ❌ Unsupported

### 7.2 Idle logic (when no enemy is detected)

| `idle` | Behavior |
|---|---|
| `stay` | Stand still |
| `explore` | Walk in one of 8 compass directions, switching every **2 seconds**. The 2 s is **fixed** (it is *not* `period`) |
| `follow` | If a teammate is detected and farther than `leash × TILE_SIZE`, walk toward the nearest one; otherwise (close enough, or no teammate seen) stand still |

### 7.3 Poison gas

If `gas` is on and gas is detected, the bot moves along `(left − right, up − down)` of the detected
gas amounts and **ignores enemy distance logic** until gas is gone. If `gas` is off, gas is treated
as always zero (no gas avoidance, and the safety filter no longer rejects gas directions).
Wall checks stay on in both cases. ✅ Confirmed (source)

⚠️ Assumed: that this vector means "away from the gas". It depends on what the engine's
`is_there_poison_gas` returns, which was not supplied.

### 7.4 Attacking

✅ Confirmed (source):

- Attack happens when `distance <= attack_range` **and** `is_enemy_hittable(...)`.
- For "must hold" brawlers (catalog-driven, `must_brawler_hold_attack`) the script presses, then
  releases after the catalog's hold time plus a global `seconds_to_hold_attack_after_reaching_max`.
- Plain auto-aim only. No aim-drags. The README states the native engine keeps authority over
  freshness, geometry and Stop/Pause gates.

### 7.5 Optional abilities

All default **off**. Fire only if `can_attack` is true, the brawler does not need hold, and no
hold is in progress. Evaluated in this order each cycle: gadget → hypercharge → super.

| Ability | Extra condition |
|---|---|
| Gadget | `is_gadget_ready` |
| Hypercharge | `is_hypercharge_ready` |
| Super | `is_super_ready` **and** `distance <= super_range` **and** `is_enemy_hittable(..., "super")` |

There is **no** health check, jump/teleport handling, enemy-count check, or per-gadget safety.
Warn the user before enabling them. ✅ Confirmed (source: the generated comment and UI warning)

### 7.6 Movement tuning facts worth knowing (derived arithmetic)

- If `range + band > 100`, enemies between 100% and `range + band` of attack range are **inside the
  hold band but out of attack range**: the bot will strafe or stand there without attacking. The
  shipped `kiter` (95+8 = 103) and `guard` (95+10 = 105) presets do this by design (a small dead
  zone). `balanced` (97) and `team` (97) do not.
- If `range − band < 0` (e.g. range 20, band 30) the retreat threshold is clamped at 0, so the bot
  never retreats.
- `range 110` means "prefer to stand beyond attack range". Almost never what a user wants.
- `band 0` makes strafing nearly impossible (the hold band has zero width) and can cause
  approach/retreat jitter around the exact distance.

## 8. Brawler Compatibility

What is proven:

- ✅ Confirmed (source): the builder **only** emits `"brawlers":["all"]` and `"gamemodes":["all"]`.
  One playstyle is meant to work for every brawler and mode.
- ✅ Confirmed (source): per-brawler adaptation happens **inside the engine**, via
  `get_brawler_range(brawler)`, `brawlers_info`, `must_brawler_hold_attack(brawler)` and the
  catalog's hold time. Distances are *percentages of that brawler's attack range*, so the same
  playstyle scales across brawlers.
- README: distances "are clamped by the engine's own limits."

What is **not** proven:

- ❓ Whether the importer accepts brawler names or game-mode names in those header arrays, and
  what exact strings it expects. No example exists. **Do not write them.** If the user wants a
  playstyle "only for Colt" or "only for Gem Grab", say the builder cannot do that, and ask for the
  importer source before attempting anything.
- ❓ Which brawlers are "must hold", and their hold times (catalog not supplied).
- ❓ The numeric value of `TILE_SIZE`.

Practical advice by brawler *type* (⚠️ Assumed game knowledge, not file-backed; confirm with the user):
short-range brawlers pair with lower `range` (≈ 35–60); long-range with higher (≈ 80–95).
Always tell the user that these numbers are starting points they should test.

## 9. AI Playstyle Generation Workflow

Follow these steps in order.

### Step A — Understand the intention

Ask **at most 2–3 short questions**, only for things you cannot infer:

1. "Should the bot stay close to enemies, keep distance, or something in between?" (→ `range`)
2. "When no enemy is visible, should it stand still, wander, or follow a teammate?" (→ `idle`)
3. "Should it automatically use Super/Gadget/Hypercharge?" (→ default **no**; warn about §7.5)

If the user already described enough, do not ask; state your assumptions in one line instead.
Never ask the user to supply numbers if a preset gets them close enough.

### Step B — Translate intentions using only supported features

| User says | Supported translation | Notes |
|---|---|---|
| "Aggressive / rush" | `rusher` preset (range 45, strafe off); or raise nothing else | Closing distance only. No "prioritize weak enemy" |
| "Defensive / safe" | `kiter` or `guard`; lower `band` for tighter spacing | There is no retreat-on-low-health: ❌ no HP logic |
| "Keep distance" | `range` 85–95, `strafe` on | Keep `range + band` near ≤ 100 if it must always close in to attack |
| "Dodge / unpredictable" | `strafe` on, shorter `period` (e.g. 1–1.5) | Not a guaranteed circular route; movement only |
| "Stay still when alone" | `idle: stay` | |
| "Wander when alone" | `idle: explore` | Interval fixed at 2 s |
| "Support / follow teammates" | `team` preset, adjust `leash` | Only when no enemy is seen; no heal/shield logic; no AFK detection |
| "Avoid gas" | `gas: true` | Local reaction only. No escape route |
| "Hold a zone / area" | `guard` (idle stay) | ❌ No map zones or coordinates. Say so |
| "Target the weakest / most dangerous enemy" | ❌ Not available | Always the closest enemy |
| "Flee below X% HP" | ❌ Not available | No HP logic |
| "Use super when 3 enemies" | ❌ Not available | Only ready + in range + hittable |
| "Use pathfinding / go to the objective" | ❌ Not available | No A*, no world coordinates |
| "Aim manually / drag aim" | ❌ Not available | Auto-aim taps only |
| "Different behavior per brawler / per mode" | ❌ Not available | See §8 |

When a request has no supported translation, **say so plainly and offer the closest supported
alternative**. Do not quietly approximate and do not invent code.

### Step C — Choose settings

1. Start from the closest preset. Change as few values as needed.
2. Keep values on the UI's step grid (§6) so the user can recreate the exact playstyle in the page.
   (This is a convention for reproducibility. The generator itself also accepts off-grid values.)
3. Check §10 for contradictions.

### Step D — Generate with the real generator

Do **not** hand-write the script. Use the generator (Appendix A) so the output is exactly what the
page would download. If you cannot run code, say so and give the user the **settings** plus
instructions to enter them in `index.html` (§12). Do not paste code you typed from memory and call
it verified.

### Step E — Validate (see §11), then deliver (see §12)

### Modifying an existing playstyle

1. If the file matches generator output, recover its settings: the header `description` shows
   `range`, `idle` and `strafe`; the body shows `desired`/`margin` factors, `now / {period}`,
   `TILE_SIZE * {leash}`, the `gas =` line and the ability block. Regenerate with changed
   settings; do not patch text in place.
2. If the file does **not** match any generator output (hand-edited or from elsewhere), tell the user
   that none of the supplied checks can vouch for it (golden hashes won't match), and offer to
   rebuild it from settings instead.
3. Preserve `name`/`author` unless asked.

## 10. Configuration Best Practices

- **Prefer presets.** They are the only combinations covered by the golden hashes (§11).
- **One idea per playstyle.** Two or three changed settings beat twelve.
- **Avoid contradictions:**
  - "Aggressive" + `range` ≥ 90 → contradiction. Use ≤ 60.
  - "Stand still, never moves" + `strafe` on / `explore` → contradiction.
  - `idle: follow` + a request to "never leave this spot" → contradiction.
  - `period` or `leash` only matter if `strafe` / `follow` is on. Don't promise effects they won't have.
  - `gas: false` + "avoid gas" → contradiction.
- **Keep abilities off unless the user asks.** If on, remind them there is no safety model.
- **Don't push to extremes** (range 110, band 0, band 30 with range < 30) unless the user
  explicitly wants them, and explain consequences (§7.6).
- **Predictable beats clever.** Pick the simplest settings that match the request.
- **Never silently clamp.** If the user asks for `range: 150`, say it is outside 20–110 and ask
  what they want (or propose 110 and *say so*). Do not just change it.
- **Never assume defaults you can't see.** If a value isn't in §6, it doesn't exist.

### 11.2 Measured results from the evidence session ✅ Confirmed (run)

- `node verify.js` on the supplied files: `PASS`, 8 checks, 0 failed.
- The generator was run for **480 combinations** (5 presets × 3 idle × strafe × gas × super ×
  gadget × hyper). All produced output with no errors. As a *sanity-only* extra, every body parsed

### 11.3 Checklist to run before delivering

1. Settings come from §6 only (12 keys, right types, in range).
2. No contradictions (§10).
3. Run the generator (Appendix A). It must not throw.
4. Run the lint snippet (Appendix B) on the output: `LINT OK`.
5. If the settings equal a preset's default toggles, compare with expected behavior in §6.1.
6. If you have the repo: run `node tools/playstyle-builder/verify.js` and, if possible,
   `./gradlew :app:testDebugUnitTest --tests com.pyla.ai.pyla.PlaystyleBuilderExportTest`.
7. If you changed anything in `index.html`, see §11.4.
8. Report **exactly** which of these you ran. If you didn't run one, say "not run".
9. If a check fails: fix the cause (not the check), regenerate, and rerun **all** checks.

### 11.4 If the user asks you to change the *builder* itself

This is not "making a playstyle"; it is changing the product. Only do this when explicitly asked.

- `verify.js` hard-codes golden SHA-256 hashes. Any generator change makes them fail **on
  purpose**. Do not "fix" it by deleting the check. Re-review the new output, then update
  `GOLDEN`, regenerate `example-export.pyla` from the real default, and update the Android test
  fixture.
- `verify.js` also pins: exactly **3 inline scripts**, the preset list/order, `connect-src 'none'`, no
  external URLs, unique element ids. Keep those true.
- Any **new** script function or variable you put in generated code is unverified until it
  exists in PylaAndroid's script API (not supplied). Do not add one on a guess (§14).

## 12. `.pyla` Export Requirements

✅ Confirmed (source + verify.js):

1. Line 1: the header JSON on **one** line (no embedded newlines; `verify.js` also checks that the
   line has a single `{`).
2. Line 2 onward: the script body, non-empty.
3. UTF-8, no BOM, **LF** line endings only, no NUL, one trailing `\n`.
4. File extension `.pyla`. Safe file names come from `fileName()`: accents stripped, anything
   other than letters/digits/`_`/`-` becomes `_`, max 64 chars before the extension, fallback
   `custom_playstyle.pyla`.
5. **Nothing else**: no Markdown fences, no explanatory prose, no extra comments, no extra
   metadata keys, no trailing text.

Name precautions (⚠️ Assumed, conservative): the generator accepts `{`, `}`, `"` and Unicode
line-separator characters (U+2028, U+2029, U+0085) in names; `JSON.stringify` escapes quotes but
leaves U+2028/U+2029/U+0085 raw. The supplied files do not show how the importer reads the header,
so **avoid `{`, `}` and those separators in names and authors**. (The verify.js line check counts
`{` characters, so a name containing `{` would trip that check.)

### How to deliver

- **If you can write files:** save the generator output as the `.pyla` file, with no changes by hand.
  Give the user the file, a short settings summary, and the verification report (§12.1).
- **If you can only chat:** do **not** paste the full script and call it done. Give the settings
  table and tell the user to open `index.html`, pick the closest preset, set those values, press
  *Download .pyla*. If they insist on code, generate it with Appendix A and put it in **one**
  code block with nothing else inside, and tell them to save as UTF-8, LF, `.pyla`.

```
Playstyle: <name>   Based on: <preset or "custom">
Settings: range=…  band=…  strafe=…(period …)  idle=…(leash …)  gas=…  super=… gadget=… hyper=…

              lint (file format): OK / not run
              verify.js: PASS / not run

### Import steps to give the user

1. Stop the bot in PylaAndroid.
2. *Playstyles → Import custom .pyla*, pick the file.
3. Select it by name.
4. Start the bot and check the logs show that playstyle is active.
   (README: a visible selection alone is not proof it runs; import success does not guarantee behavior.)
5. If import fails, keep the file and the exact error message and share them for diagnosis.

## 13. Common Mistakes and How to Avoid Them

| Mistake | Why it matters | Do this instead |
|---|---|---|
| Writing a script by hand | May be unparsable; none of the checks cover it | Always use the generator |
| Adding header keys like `"version"`, `"priority"`, `"brawler"` | Not in the generator. Importer behavior unknown | Use only the 5 keys in §5.1 |
| `"brawlers":["colt"]` or `"gamemodes":["gemGrab"]` | Never seen; unknown accepted strings | Use `["all"]`, explain the limit |
| Calling functions you "know" from other bots | May not exist in PylaAndroid's API; PC helpers aren't supported | Only identifiers in Appendix C |
| Promising "safe", "smart", "win more" | No HP/threat logic; no gameplay test | Describe movement, not outcomes |
| Saying "verified" after only reading the code | Misleading | Say which checks you actually ran |
| Silently changing the user's out-of-range number | Hides a real problem | Tell them and ask |
| Booleans as strings (`"true"`) | Rejected | Real `true`/`false` |
| Using `period` with `strafe` off | No effect | Don't claim it does |
| Using `leash` unless `idle: follow` | No effect | Same |
| Thinking `explore` uses `period` | It's a fixed 2 s | Don't promise tunable exploring |
| Wrapping the file in ``` fences or adding a preface | Breaks the format | Raw file only |
| Windows `\r\n` or a BOM from an editor | Breaks format rules | LF, UTF-8, no BOM |
| Editing `verify.js` goldens to make it pass | Defeats the gate | §11.4 |
| `range + band` far above 100 while the user wants constant attacking | Dead zone with no attacks | §7.6 |
| Treating the Python `ast` pass as PylaAndroid parsing | Different parser | It's only a sanity hint |

## 16. Instructions for Future AI Agents

1. **Be a helpful guide, not a gatekeeper.** Many users have never coded. Use plain words. Explain
   a setting in one sentence ("*range* = how close it likes to stay to enemies, as a share of its
   shooting range").

3. **Say "can't" kindly and early**, with the nearest supported option.
4. **The generator is the spec.** If this document and the code ever disagree, trust the code, and
   tell the maintainer the document needs an update.
5. **Evidence over confidence.** Never write "verified", "tested" or "compatible" unless you ran the
   check *in this session* and can name it.
6. **Ask when information is missing**; don't guess identifiers, strings or defaults.
7. **Re-run all checks after any change.** Never deliver a playstyle you know is invalid.
8. **Keep this file up to date** when you change the builder: new settings → §6, §7, tests,
   goldens, example export, and the Android test fixture.

// Usage: node gen.js config.json [out.pyla]
const fs = require('fs'), vm = require('vm');
const html = fs.readFileSync(__dirname + '/index.html', 'utf8');

## Appendix B — Format lint for any `.pyla` (tested)

Save as `lint.js`. Run: `node lint.js file.pyla`. This checks **file format only** (layer 1).
It is not a PylaAndroid parse.

```js
// Usage: node lint.js file.pyla  -- structural sanity only; NOT a PylaAndroid parse.
const fs = require('fs');
const t = fs.readFileSync(process.argv[2], 'utf8');
const errs = [];
if (t.charCodeAt(0) === 0xFEFF) errs.push('BOM present');
if (t.includes('\r')) errs.push('CR found (LF only)');
if (t.includes('\u0000')) errs.push('NUL found');
if (/[\u2028\u2029\u0085]/.test(t.split('\n')[0])) errs.push('exotic line separator in header');
const lines = t.split('\n');
let h; try { h = JSON.parse(lines[0]); } catch (e) { errs.push('line 1 is not JSON: ' + e.message); }
if (h) {
  const keys = Object.keys(h).join(',');
  if (keys !== 'name,description,brawlers,gamemodes,author') errs.push('unexpected header keys: ' + keys);
  if (typeof h.name !== 'string' || !h.name.trim()) errs.push('name must be a non-empty string');
  if (JSON.stringify(h.brawlers) !== '["all"]') errs.push('brawlers != ["all"] (only value evidenced)');
  if (JSON.stringify(h.gamemodes) !== '["all"]') errs.push('gamemodes != ["all"] (only value evidenced)');
  if (lines[0].split('{').length !== 2) errs.push('header must be one line with a single "{"');
}
if (!lines.slice(1).join('\n').trim()) errs.push('empty body');
if (/^```/m.test(t)) errs.push('Markdown fence inside file');
if (/\t/.test(t)) errs.push('tab characters (generator uses 4 spaces)');
console.log(errs.length ? 'LINT FAIL\n- ' + errs.join('\n- ') : 'LINT OK');
process.exit(errs.length ? 1 : 0);
```

Tested: it returns `LINT OK` for `example-export.pyla`.
